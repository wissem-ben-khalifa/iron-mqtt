## Key findings (details in the sections below)

1. **TLS blinds a default Suricata deployment.** With its stock TLS setting
   (`encryption-handling: track-only`) Suricata raised **0 alerts** on the compromised-device
   flood in test-B; only after switching to `full` inspection did its rate rule catch 19/19 flood
   windows (F1 0.864). It never sees MQTT, and in TLS 1.3 it never sees certificates. (Core A)
2. **The insider's TLS fingerprint matches the fleet.** The attacker runs the genuine device
   software, so its JA3/JA4 equals every device's; fingerprint rules cannot single it out (they
   did catch foreign client tooling). (Core A)
3. **The ML model relies only on features the attacker produces.** `m0001` puts 100% of its
   importance on five upstream features generated by the device's own sending behaviour; none
   of its 19 features is outside the device's influence. (Core B, `docs/FEATURES.md`)
4. **The MVP flood is easy for every detector** (recall 1.0 for ML, threshold and Suricata-`full`
   on test-B); the differences are false alarms: ML 0/hr, threshold 4.2/hr, Suricata 12.6/hr. (M6, Core A)
5. **MQTTset is a synthetic testbed:** perfectly periodic benign traffic; within-MQTTset F1 1.0 but
   MQTTset→fleet precision 0.42. (M6)
6. **Robust features cut reliance on device-produced signals without losing detection**: weight on
   "YES" features 100% (m0001) → 77% (m0002) → 0% (m0003), all F1 1.0 on test-B. But attribution
   still needs per-source volume (system-only per source: recall 0.00), and the only fully
   device-independent signal, honest-device latency, detects the attack (F1 0.895) 5 s later and
   cannot say who. For a volumetric flood, volume is both the signal and the attacker's control. (Core)

## Feature spike — fleet vs MQTTset, same extractor (2026-10-15, corrected re-run)

Command: `./iron spike` (`ids/spike.py`). Fleet = all `captures/live` chunks up to 13:50 UTC
(~75 min, **fleet IPs 172.28.0.101–110 only**); MQTTset legit = first 300k packets of
`capture_1w.pcap` (4.2 h, `editcap -r ... 1-300000`); MQTTset flood = `capture_flood.pcap`.
Descriptive only; no model is involved.

**What is measured:** the **TCP payload length** (bytes after the TCP header) of
client→broker segments that **carry payload**; **empty ACKs are excluded** (in the fleet
sample 1,037 empty ACKs vs 2,006 data segments; MQTTset legit 109,390 empty ACKs).
Correction: the first run also counted the tests container (172.28.0.250) in the fleet
size line; it is now filtered out. The first run's fleet median was 181 B; corrected 193 B.

Windows: fleet 2,823 (10 clients), MQTTset legit 16,505 (10 clients), MQTTset flood 42 (1 client:
192.168.1.100, a single TCP connection — the flood pcap contains only the attacker).

| Source | segments | min | median | p95 | max |
|---|---|---|---|---|---|
| **Our fleet**, MQTT over TLS 1.3 | 4,583 | 24 | **193** | 1,446 | 1,598 |
| **MQTTset** legit, plaintext MQTT | 79,676 | 2 | **13** | 14 | 37 |
| **MQTTset** flood, plaintext MQTT | 299 | 37 | 32,759 | 32,760 | 32,768 |

Sanity check of the TLS floor (independent tshark run): the smallest fleet segment is
24 B = 5 B TLS record header + 19 B record, i.e. a 2-byte MQTT PINGREQ + 1 B inner content
type + 16 B AEAD tag. No fleet segment is below the TLS overhead floor, so a 13 B median
can only come from plaintext (MQTTset), as expected.

Per-window features, p50 / p95:

| Feature | Fleet | MQTTset legit | MQTTset flood |
|---|---|---|---|
| pkts_up | 2 / 7 | 10 / 15 | 7 / 10 |
| bytes_up | 265 / 3,540 | 590 / 845 | 182,000 / 281,000 |
| data_pkts_up | 1 / 5 | 5 / 6 | 7 / 10 |
| payload_up_mean | 189 / 592 | 13 / 14 | 27,000 / 30,600 |
| iat_up_mean (s) | 5 / 5 | 1 / 1.5 | 0.50 / 0.67 |
| pkts_down | 1 / 6.9 | 5 / 10 | 7 / 10 |
| bytes_ratio_up_down | 3.9 / 5.0 | 1.8 / 1.8 | 513 / 588 |

**What this means (no spin):**
1. **Size features do not transfer.** Under TLS no segment is as small as MQTTset's 13-byte
   plaintext publishes (TLS adds ~22–29 B per record), and MQTTset's flood segments
   (32 KB, Linux cooked capture with 64 KB MSS) cannot occur on a 1500-MTU Docker bridge.
2. **Count/timing features are partly comparable**, but MQTTset's benign clients are
   ~5× chattier than our periodic devices and extremely uniform (p50≈p95).
3. Consequence for M6: the IDS is trained and tested on **fleet** traffic (separate runs).
   MQTTset is used for the planned transfer test in both directions, and the gap is
   expected to be large because of (1); that number will be reported, not hidden.
   A resegmentation transform (split MQTTset segments to a 1448-byte MSS) is a possible
   mitigation; it is noted, not built.

## Timing transfer: MQTTset vs fleet (2026-10-15)

Method (`ids/timing.py`, identical for both): client→broker TCP segments with payload
(empty ACKs excluded); keepalives removed — MQTTset filtered to MQTT PUBLISH (first byte
type 3), fleet with 24-byte segments (TLS record carrying a PINGREQ) removed; fleet status
heartbeats (every 60 s) are PUBLISHes and stay in. Per client: rate, median gap,
CV = std/mean of gaps, burstiness B = (σ−μ)/(σ+μ) (−1 periodic, 0 Poisson, →1 bursty).

MQTTset legitimate traffic, 4.2 h at the start of the week **and** 4.2 h mid-week
(2020-06-15 22:18 → 06-16 02:32) — identical:

|---|---|---|---|---|
| 5 (…154, 155, 174, 176, 180) | 60.0 | 1.0 s | 0.000–0.001 | −0.999 |
| 3 (…151, 152, 178) | 1.0 | 60 s | 0.0 | −1.0 |
| 1 (…173) | 0.5 | 120 s | 0.0 | −1.0 |
| 1 (…150) | 0.34 | 180 s | 0.0 | −1.0 |

Fleet, clean run (13:43:40–14:08:40, profile p1):

| device (type) | rate/min | median gap | CV | B |
|---|---|---|---|---|
| 101, 105, 107 (env_sensor) | 13.0 | 4.96 s | 0.22–0.23 | −0.63 |
| 102, 106, 108 (smart_plug) | 7.05 | 9.9 s | 0.35–0.37 | −0.46 to −0.48 |
| 103 (door_sensor) | 2.46 | 18.5 s | 0.81 | −0.10 |
| 109 (door_sensor) | 3.73 | 12.2 s | 0.95 | −0.03 |
| 104 (camera) | 19.96 | 0.5 s | 3.57 | +0.56 |
| 110 (camera) | 20.64 | 0.5 s | 3.69 | +0.57 |

**Finding:** MQTTset's 10 clients are strictly periodic (B = −1, CV ≈ 0) with fixed gaps
of 1/60/120/180 s; there is no event-driven or bursty client. Our fleet spans periodic
(env, plugs), Poisson-like (doors, B ≈ 0) and bursty (cameras, B ≈ +0.57) behaviour.
Per the decision rule, MQTTset's timing is not a realistic calibration target for
event-driven devices, so **profiles are kept (p1)** and no re-baseline is needed.
Neither sizes nor timing transfer; MQTTset remains useful only for the M6 transfer-gap
number and as a "strictly periodic sensor" reference.

### Notes on MQTTset realism (2026-10-15)

- **MQTTset benign traffic is perfectly periodic (B = −1, CV ≈ 0), so it is a synthetic
  testbed, not a realism reference.** Our device profiles are designed from device-type
  *behaviour* (periodic sensors, event-driven doors, bursty cameras); the public dataset
  itself is periodic, so it cannot be cited as evidence that our timing is realistic. We
  state this openly rather than claiming MQTTset validates our fleet.
- **Hypothesis for the M6 transfer test (not a claim):** published MQTTset classifier
  scores of 98%+ may come largely from separating its 32 KB flood from perfectly periodic
  1-second benign traffic — an easy split. Whether that is so will be tested in M6 (train
  on fleet, test on MQTTset and vice versa) and reported as a measured number, not asserted.

## M5 — MQTT flood from a compromised device, impact measured (2026-10-15)

Attack: a compromised device (device-07, valid cert) floods `devices/device-07/telemetry`
from the attacker agent (172.28.0.40), reusing the device client code. Triggered via
`POST /attacks/flood`; ground truth in the `runs` collection. Impact is measured on the
**9 honest devices** (device-07 excluded) over the 30 s generation window vs a 20 s benign
window just before, profile p1. Command: `./iron attack-check --rate R --duration 30 --qos 0`.

| target rate | sent | achieved/s | honest p50 benign→attack | honest p95 benign→attack | p95 ×| honest loss |
|---|---|---|---|---|---|---|
| 500/s | 15,000 | 500.0 | 0.82 → 8.79 ms | 1.09 → 17.5 ms | 16× | 0 |
| 2,000/s | 59,933 | 2,000.2 | 0.78 → 2.51 ms | 1.04 → 4.9 ms | 4.7× | 0 |
| 20,000/s | 598,415 | 19,972.7 | 0.83 → **1590 ms** | 0.93 → **1960 ms** | ~2100× | **1** |

Resource use during a 20k/s flood (host `docker stats`, benign → attack):
broker 0.05% → ~21% (one core), **ingest 0.2% → ~100% (one core saturated)**, mongo 1.2% → 26–62%.

**Honest finding.** This is a **telemetry-pipeline DoS, not a network flood.** The broker
and 11 of 12 cores stay idle; the bottleneck is the single ingest consumer. At ≤2,000/s
ingest keeps up and honest telemetry is only delayed a few ms with no loss. At 20,000/s
ingest saturates: honest messages are delayed ~1.6–2.0 s (freshness destroyed) and loss
begins (1 message). So the flood degrades **freshness before availability**, exactly the
kind of effect a volumetric threshold and the ML IDS should both catch — which is why the
MVP expects the threshold to match the ML model here (the ML model earns its place on the
low-rate/evasive variants in the core tier). The 500/s vs 2,000/s p95 inversion is
small-sample noise (15–30 honest messages per window at ms-level impact); the clear signal
is the jump at saturation.

Scope check (verified): the attacker refuses any target other than the broker service
(`BROKER_HOST=8.8.8.8` and `evil.example` both rejected at startup). Ground truth stored:
rate, qos, sent, gen_seconds, achieved rate, attacker IP, profile_version=p1.
Raw: `captures/runs/m5/sweep_{500,2000,20000}.json`.

## M6 — Offline IDS: supervised classifier vs threshold (2026-10-15)

Two labelled runs, generated by `scripts/run_experiment.py`, labelled from the run manifest
(ground truth: attacker IP + attack time windows), never from a model. Per-source 5 s windows,
TLS-visible features only (`ids/features.py`); the client IP is the label join key, not a feature.
- **train-A** (fleet seed 1): warm-up + floods at 800/s and 4000/s + cool-down → 606 windows (38 attack).
- **test-B** (fleet seed **2**, unseen rate **2000/s**): 362 windows (19 attack). Separate run, different
  benign behaviour and an attack rate not in training.

Model: scikit-learn `GradientBoostingClassifier` (`m0001`, registered in `models` with training
lineage). Top features: `payload_up` 0.41, `iat_up_min` 0.36, `payload_up_std` 0.09.

Evaluation on test-B (`./iron evaluate --model m0001 --train train-A --test test-B`):

| detector | precision | recall | F1 | TP | FP | FN | TN | false alarms/hr |
|---|---|---|---|---|---|---|---|---|
| ML (gradient boosting) | 1.000 | 1.000 | **1.000** | 19 | 0 | 0 | 343 | 0.0 |
| threshold (`payload_up > 13,737 B/window`) | 0.905 | 1.000 | 0.950 | 19 | **2** | 0 | 341 | 4.2 |

Sanity: a model trained on **shuffled** labels scores F1 **0.0** on test-B (chance), far below 1.0.

**Honest reading.** As the MVP predicted, a volumetric flood is easy: both detectors catch every
attack window (recall 1.0). The difference is false alarms — the threshold fires on 2 legitimate
**camera-burst** windows (cameras send ~1 KB detections at 2 Hz, briefly exceeding the byte
threshold); the ML model avoids them by also using inter-arrival timing (`iat_up_min`). So on the
MVP flood the ML model's advantage is modest (fewer false positives), which is why the adversarial
value is in the core tier (low-rate and evasive variants), not here.

### MQTTset transfer test — the hypothesis, measured (`./iron transfer`)

| setting | precision | recall | F1 |
|---|---|---|---|
| within-fleet (train-A → test-B) | 1.00 | 1.00 | 1.00 |
| within-MQTTset (random half → half) | 1.00 | 1.00 | **1.00** |
| fleet → MQTTset | 1.00 | 0.88 | 0.94 |
| MQTTset → fleet | **0.42** | 1.00 | **0.59** |

**Finding (supports, does not prove, the hypothesis).** Within MQTTset the split is trivially
perfect (F1 1.0): its 32 KB flood vs perfectly periodic benign traffic is linearly separable, so a
headline 98%+ on MQTTset says little about real detection. A model trained on MQTTset transfers
**poorly to the realistic fleet** (precision 0.42 — it false-alarms constantly, because MQTTset's
learned byte scale does not fit TLS traffic). The fleet→MQTTset direction is easier (0.94) only
because MQTTset's flood is so extreme any sensible model flags it. This is the measured realism gap
we report rather than hide. Raw: model `m0001`; data in `captures/runs/{train-A,test-B}`.

First-alert is bounded below by the pipeline: the sensor rotates a chunk every 5 s and the
detector processes all-but-newest while polling every 2 s, so an attack is detected within
roughly one chunk (~5–7 s of its start); the per-window latency above is the extra delay once
a window has closed, which is sub-2 s.

The `/incidents/timeline` aggregation groups these into 30 s buckets per source with the
model versions involved — the NoSQL timeline-reconstruction query over nested incidents.

## Core A — Suricata baseline on the same test-B run (2026-10-15)

**What Suricata can and cannot see here (stated plainly).** All fleet traffic is MQTT over
TLS 1.3. Suricata cannot decrypt it, so it has **no MQTT visibility at all**. It is limited to:
(1) flow/volume signals — packet counts and rates per source; (2) the cleartext part of the
TLS 1.3 handshake — the ClientHello (SNI, JA3/JA4 fingerprints). **Certificates are encrypted
in TLS 1.3**, so certificate-field rules cannot apply to this fleet. This is a property of the
deployment (encryption working as intended), not a weakness of Suricata.

**Facts measured before writing rules** (Suricata 8.0.7, eve `tls` events):
- All 10 devices, ingest, the API **and the attacker (172.28.0.40)** present the identical
  JA3 `e459f9ec156647e137eec3618527db1f` / JA4 `t13d171200_ab0a1bf427ad_ecd0401ec68b`, because
  the attacker reuses the device client code (a deliberate design choice).
- No certificate fields in any TLS 1.3 handshake; only the TLS 1.2 evidence sessions expose them.

**Rule set** (`suricata/iron.rules`, generated by `ids/suricata_compare.py fit-rules`, fitted
on train-A and on benign M2 handshakes — never on test-B):

| sid | type | rule |
|---|---|---|
| 9000001 | handshake | TLS ClientHello to the broker whose **JA4** is not the fleet's |
| 9000002 | handshake | same, **JA3** |
| 9000010 | flow/rate | ≥ **12** upstream data packets from one source within 5 s (`threshold type threshold, track by_src`); 12 = the `data_pkts_up` cut that maximised F1 on train-A |

Excluded from the comparison: an IP/identity rule ("broker traffic from a non-device address")
would flag the attacker trivially, but ground truth is defined by IP, so it would be circular —
the same reason the ML features exclude IPs.

**Sanity — the handshake rules do work:** on the M2 capture they fire on the rogue/evidence
tooling at 172.28.0.250 (4 × JA4, 4 × JA3: Python-`ssl` raw clients with a different
ClientHello), and never on the 10 fleet devices.

**Command:** `./iron suricata` (identical windows: `ids.labeling` on test-B, 362 windows,
19 attack / 343 benign; all detectors scored on the same keys).

| detector (test-B) | precision | recall | F1 | TP | FP | FN | TN | false alarms/hr |
|---|---|---|---|---|---|---|---|---|
| ML (gradient boosting, m0001) | 1.000 | 1.000 | **1.000** | 19 | 0 | 0 | 343 | 0.0 |
| threshold `payload_up > 13,737 B/window` | 0.905 | 1.000 | 0.950 | 19 | 2 | 0 | 341 | 4.2 |
| **Suricata, default config** (`encryption-handling: track-only`) | — | **0.000** | 0.000 | 0 | 0 | 19 | 343 | 0.0 |
| Suricata rate rule (`encryption-handling: full`) | 0.760 | 1.000 | 0.864 | 19 | 6 | 0 | 337 | 12.6 |
| Suricata JA4/JA3 rules | — | 0.000 | 0.000 | 0 | 0 | 19 | 343 | 0.0 |
| Suricata, all rules (`full`) | 0.760 | 1.000 | 0.864 | 19 | 6 | 0 | 337 | 12.6 |

**Reading it honestly:**
1. **Out of the box, Suricata does not alert on this flood at all.** Its default TLS mode keeps
   tracking a session but stops inspecting packets once the session is encrypted, so the rate
   rule is never evaluated. With `encryption-handling: full` it catches every flood window
   (3,328 alerts from 172.28.0.40). Operators would have to choose that mode deliberately (it
   costs throughput).
2. **The fingerprint rules are blind to this attacker by construction**: a compromised device
   running the genuine device software has the genuine fingerprint. They remain useful
   against foreign client software (they caught the M2 rogue tooling).
3. **The rate rule's 6 false-positive windows** are all at 14:46:30–32: the reconnect burst when
   the containers were restarted just before the run (CONNECT, SUBSCRIBE, retained status —
   many small packets). In the steady-state benign period it raised none. A packet-count rule is
   sensitive to reconnect storms (e.g. after a broker restart); the byte threshold and the ML
   model were not, on the same windows.
4. So on this volumetric MVP flood: ML 1.000 F1 ≥ threshold 0.950 ≥ Suricata (`full`) 0.864, all
   three with recall 1.0 — the difference is false alarms. This is a fair, single-run comparison
   on identical input; it is **not** a claim that Suricata is weak — it is working without the
   payload visibility it normally relies on.

## Core — Robust-feature models vs m0001 on test-B (2026-10-16)

Approach: defensive feature engineering (no evasion step).
New features (`ids/robust_features.py`), provenance classes as in `docs/FEATURES.md`:
broker fan-out to ingest (`fanout_payload`, PARTIAL), ingest TCP backpressure
(`ingest_rwnd_min`, `ingest_zero_win`, SYSTEM), fleet upstream volume (`fleet_up_payload`,
PARTIAL), number of active sources (`active_sources`, SYSTEM), the source's share of fleet
volume (`share_up`, PARTIAL), and the **collateral impact on honest devices**

### The honest limit for a volumetric flood

For this attack, **volume is both the signal and the thing the attacker controls.** The
measurements above show what that means in practice:

1. **Attribution needs per-source volume.** Every model that identifies *which* source is
   attacking relies on that source's own traffic volume, directly (m0001, m0002) or as a share
   of the fleet (m0003, 100% `share_up`). Remove per-source volume and attribution fails
   completely: m0004 has recall **0.00** (system signals are identical for every source in a
   window).
2. **Signals the device cannot set measure the effect, not the cause.** The collateral-latency
   model (m0006, 100% SYSTEM weight) detects that an attack is in progress with F1 0.895, but it
   is **5 s slower** (8.46 s vs 3.46 s), misses windows where the attack is only beginning or
   ending, raises false alarms on benign disruptions (restarts), and cannot say who is attacking.
3. **The effect signal only exists while there is harm.** It fires because honest devices are
   slowed (median 0.77 → 2.01 ms here). A flood too weak to slow honest devices would also be
   invisible to it — and, by the same measurement, not harming them. In M5 the harm was
   measurable at every rate we ran, **500 to 20,000 msg/s** (at 500/s honest p95 1.09 → 17.5 ms).
   **We have no measurement below 500 msg/s**, so where a flood becomes both undetectable by
   this signal and harmless is **not measured** and is not claimed here.

So the realistic robust design is two-stage: a system-level stage that no single device can
silence (collateral latency, fan-out, backpressure) decides *whether* the system is under
attack; per-source volume then attributes it. The second stage remains attacker-influenced by
nature for a volumetric attack — that is the limit, not a fixable modelling flaw.

Deployment note: these models are evaluated offline. Running them live needs the detector to
read telemetry (its MongoDB role currently cannot) and to compute the system features per
window; not done yet. Raw: `captures/runs/robust/robust-test-B.json`.
